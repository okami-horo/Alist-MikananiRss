## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **Scope**: Clearly identify which core modules are in scope for this feature (e.g., RSS monitor, extractor/LLM, renamer, Alist/WebDAV integration, notification bots, database, bot assistant, CLI/web UI).
- **Architecture fit**: The design MUST align with the existing async, modular Python 3.11+ architecture and SHOULD reuse existing packages, patterns and directories where possible (see `AGENTS.md`). Introducing new services or infrastructure requires explicit justification in this plan.
- **Testing discipline**: The plan MUST describe tests for core logic in line with the Test-First principle — unit tests for isolated logic and integration tests for flows that cross modules (e.g., RSS → download → rename → notify). Any intentional gaps MUST be documented and justified.
- **Observability & failure handling**: For new flows and external integrations (Alist/WebDAV, RSS sites, LLM providers, Telegram/PushPlus, etc.), the plan MUST specify logging, error handling and, where meaningful, metrics/alerts (e.g., RSS parse failures, WebDAV path errors, LLM timeouts).
- **Breaking changes & migration**: Any behavior, config, CLI/entrypoint or WebUI change that may break existing usage MUST document versioning impact, migration steps and backward-compatibility strategy, or explicitly record a consciously accepted breaking change.
