### User Story 1 - 通过浏览器管理订阅系统的日常运行 (Priority: P1)

作为在 NAS / 服务器上自部署本项目的维护者，我希望在浏览器中打开 WebUI，就可以直接查看系统状态、启动或停止订阅监控，而不需要再登录 SSH 执行命令行，这样日常使用更简单也不依赖命令行能力。

**Why this priority**: 这是日常使用频率最高的路径，也是“去命令行化”的核心价值所在，没有它就不能称为 Web 驱动的系统。

**Independent Test**: 在一台全新部署的机器上，只通过浏览器访问 WebUI，完成系统启动与停止的完整闭环（包括看到状态变化），全程不执行任何项目自带 CLI 子命令。

**Acceptance Scenarios**:

1. **Given** 后端服务已作为守护进程或容器启动但尚未开启订阅监控，用户在浏览器中打开 WebUI 仪表盘，**When** 点击“启动订阅”按钮，**Then** 仪表盘状态从“已停止”变为“运行中”，并显示运行时长开始累加。
2. **Given** 订阅监控正在运行，**When** 用户在 WebUI 中点击“停止订阅”，**Then** 系统状态变为“已停止”，后端不再轮询 RSS 但服务进程本身保持存活，WebUI 仍可正常访问。

### User Story 2 - 通过 WebUI 完成系统的初始配置与重配置 (Priority: P1)

作为首次部署本项目的使用者，我希望通过 WebUI 填写或修改 Alist 地址、Token、RSS 订阅 URL、重命名与 WebDAV 等核心配置，并能够在保存前做基础校验和连通性测试，这样可以不用手改 `config.yaml` 也能完成配置。

**Why this priority**: 没有可视化配置能力，用户仍然需要编辑 YAML 文件并重启服务，与“前端完全控制后端”目标不符。

**Independent Test**: 在没有现成配置文件的环境中，仅通过 WebUI 完成配置的创建、保存与测试，并且保存后立即可以通过 WebUI 控制订阅运行。

**Acceptance Scenarios**:

1. **Given** 服务器上不存在有效配置文件，**When** 用户首次访问 WebUI 的配置页面并填写 Alist 地址、Token、订阅 URL 等信息点击“保存”，**Then** 系统在后端生成配置文件并返回“保存成功”，随后仪表盘能正确显示基于该配置的状态。
2. **Given** 用户修改了 Alist 地址或 Token，**When** 点击“测试配置”，**Then** 后端对新配置进行校验并真实请求 Alist，成功时给出“连接正常”，失败时清晰展示错误原因（如 HTTP 状态码、网络错误等）。

### User Story 3 - 通过 WebUI 诊断问题并执行维护操作 (Priority: P2)

作为维护者，当下载或重命名出现异常时，我希望可以在 WebUI 中查看详细日志、过滤搜索关键字，并且可以从同一个界面触发 WebDAV 嵌套目录修复等维护任务，而不是切到命令行查日志和运行脚本。

**Why this priority**: 问题诊断与修复是长期运维的高价值场景，能显著减少排查成本，虽然频率低于日常启停与配置，但对整体体验影响较大。

**Independent Test**: 在模拟出现错误的环境下，仅通过 WebUI 即可定位问题日志，并触发一次 WebDAV 修复任务得到结果反馈，无需命令行参与。

**Acceptance Scenarios**:

1. **Given** 系统运行中日志文件中包含错误记录（例如 WebDAV 访问失败、下载任务失败），**When** 用户在日志页面按关键字或级别筛选，**Then** 能在 2 秒内看到过滤结果，并可以点开单条日志查看详细信息。
2. **Given** 某个目录存在 WebDAV 嵌套结构问题，**When** 用户在 WebUI 的 WebDAV 修复页面指定目标目录并触发“预览”或“实际执行”，**Then** 后端会在合理时间内完成任务并返回统计结果（总条目、成功数、跳过数、错误数等），页面清晰展示结果。

---

### User Story 4 - 在多终端上安全访问与使用 (Priority: P3)

作为同一局域网中的多个使用者，我希望可以在不同终端（PC、平板、手机浏览器）上访问 WebUI，查看当前状态和最近活动日志，但只有被授权的维护者可以修改配置或调整订阅运行状态，这样既方便观察，又避免误操作。

**Why this priority**: 多终端访问提升便利性，基础只读访问风险较小；写操作需要一定的访问保护，以避免误触或未授权修改。

**Independent Test**: 在同一网络下用两台设备访问 WebUI，一台以维护者角色进行写操作，一台仅浏览状态与日志，验证权限控制与多终端展示都能正常工作。

**Acceptance Scenarios**:

1. **Given** 系统配置了基础的访问控制策略（例如简单口令或反向代理 ACL），**When** 未授权用户访问配置或维护页面，**Then** 系统会拒绝写操作或引导到只读界面，而不会影响整体服务可用性。
2. **Given** 两个终端同时打开仪表盘，**When** 其中一个终端通过 WebUI 启动或停止订阅，**Then** 另一终端在下一次状态刷新时能够看到状态变化，避免状态信息不一致。

### Edge Cases

- 当后端服务进程未启动或异常退出时，用户直接访问 WebUI 域名会看到什么？需要提供清晰的“服务不可用/后端未运行”提示，而不是空白页或浏览器错误。
- 当配置文件缺失或损坏时，WebUI 应自动进入“引导配置模式”，而不是直接报 500 错。
- 当长时间运行的维护任务（如大目录的 WebDAV 修复或批量重命名）执行中，用户刷新页面或关闭浏览器，再次打开时如何恢复任务状态展示？
- 当有多个用户同时编辑配置时，应如何避免配置被互相覆盖（例如最后写入者覆盖所有字段）？
- 在网络波动或 Alist/TMDB/外部服务暂时不可用时，WebUI 相应的测试/状态接口应有明确的失败信息与重试建议，而不是长时间卡住。

## Clarifications

### Session 2025-11-22

- Q: WebUI 的“配置修改 / 运维操作”访问控制在默认部署中由谁负责？ → A: 选项 B：仅由外部反向代理 / 部署环境提供访问控制，本项目本身不实现内置登录鉴权。
- Q: 当多个用户几乎同时通过 WebUI 编辑并保存配置时，应采用怎样的冲突处理策略？ → A: 选项 A：采用“最后写入者覆盖”语义，不实现版本号/编辑锁等并发控制，默认视为单人运维场景。
 - Q: 已有旧版命令行部署的用户，其现有 `config.yaml` 在升级到 WebUI 版本时是否需要强向后兼容？ → A: 选项 C：不强制保证旧配置可直接沿用，推荐在 WebUI 中重新创建配置，代码层面仅“尽量读取、失败视为合理”。
 - Q: 重构后官方推荐的默认部署模式是什么？ → A: 选项 A：单体部署，由后端服务同时提供 API 与前端静态资源，官方 Docker 镜像采用单容器一体化形态。
 - Q: 日志和任务状态在 WebUI 中的更新方式要求是怎样的？ → A: 选项 A：前端通过短轮询（例如 2–5 秒）请求最新日志片段和任务状态，后端提供分页或游标接口，不实现 WebSocket/SSE 等实时推送机制。
 - Q: 针对 US4 的“只读/敏感操作”隔离，路径划分如何落地？ → A: 采用路由前缀分区：`/api/public/*` 暴露状态与日志只读接口，`/api/admin/*` 暴露启停、配置与 WebDAV 修复等敏感接口，旧的 `/api/system|config|webdav` 作为兼容入口存在，但推荐在代理层仅放行 `/api/public/*`。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须以长期运行的后端服务形式提供能力，对外暴露统一的 HTTP API，用于控制 RSS 监控、下载任务管理、重命名与 WebDAV 修复等核心功能；后端服务本身不因订阅任务的启停而退出。
- **FR-002**: 原有通过命令行子命令（如 `monitor`、`webdav-fix`）提供的业务能力，必须通过后端 API 全量暴露给 WebUI 使用，使用户在正常使用场景下不再需要执行项目自带的命令行入口。
- **FR-003**: WebUI 必须能够基于后端 API 完成订阅系统的启停控制，包括：查询当前运行状态、启动订阅循环、停止订阅循环、在需要时触发“重启订阅”操作。
- **FR-004**: WebUI 必须提供完整的配置管理能力，包括：
  - 读取当前生效配置并在表单中展示；
  - 编辑并保存配置，保存时进行基础字段校验；
  - 提供“测试配置”操作，对关键外部依赖（如 Alist、RSS 源）做连通性检查并返回结果；
  - 在保存前后保持配置文件的一致性和备份（例如生成备份文件）。
- **FR-005**: 系统必须提供基于配置的多源订阅管理能力，允许在 WebUI 中增加、修改和删除 RSS 订阅 URL 以及过滤/重命名相关规则，后端监控逻辑基于最新配置生效。
- **FR-006**: 系统必须提供日志浏览与检索接口，支持按文件、级别、关键词查询最近日志，并支持按时间顺序流式查看新增日志，以便 WebUI 实现“最近活动”和日志页面功能。
- **FR-007**: 系统必须提供 WebDAV 嵌套结构修复的 API，包括“预览模式”（不执行真实写入，仅返回计划操作）和“执行模式”（实际变更远端文件结构），并返回结构化的统计与详情，供前端展示。
- **FR-008**: 对于可能运行较久的操作（如大目录的 WebDAV 修复或批量重命名），后端必须以任务的形式管理，并允许前端轮询或订阅任务状态，避免长时间占用单个 HTTP 请求导致超时。
- **FR-009**: 系统必须支持在多终端同时访问的情况下保持状态一致性，至少在每次前端显式刷新或轮询时，能获取到后端的真实状态（例如订阅是否在运行、当前配置版本等）。
- **FR-010**: 系统必须提供基础的访问保护能力，用于限制配置修改和运维操作（例如启停订阅、执行 WebDAV 修复），可以依赖简单内置机制（如共享口令）或部署层面的访问控制，但在设计上要为这些敏感操作预留权限边界。

### 非功能性与范围约束（补充说明）

- 本次重构的主要目标是交互方式和进程角色的调整，核心抓取、下载、重命名等业务算法保持现有行为不变，除非为满足 Web 控制需要而做的必要改造。
- 运行环境仍然假定为可信的内网或自控环境，本规范不要求实现完整的多用户账户体系，只需支持区分“只读访问”和“敏感操作”两类能力的访问控制边界。
- 默认假定 WebUI 的访问控制（含“谁可以修改配置 / 执行维护操作”）由外部反向代理、NAS 或容器编排环境提供，本项目后端不实现内置登录鉴权，仅在 API 设计上区分只读与敏感操作边界以便外部控制。
 - 配置编辑语义为“最后写入者覆盖”，不实现版本号、编辑锁等并发控制机制，典型部署场景为单人或少数维护者协作。
 - 旧版命令行部署生成的 `config.yaml` 不保证可在新版本中无缝兼容，默认推荐用户在 WebUI 中重新创建配置；实现上可以在不显著增加复杂度的前提下尝试读取旧配置作为初始值来源，但失败属于可接受行为。
 - 默认推荐部署形态为单体服务：由后端进程同时提供 HTTP API 与前端构建产物，官方 Docker 镜像以单容器一体化为主；进阶用户可以通过反向代理等手段自定义前后端分离部署。
 - 日志与任务状态更新采用短轮询方案：前端按约定间隔（如 2–5 秒）发起 HTTP 请求获取增量日志和任务状态，后端通过分页或游标避免一次性返回过多数据，不提供 WebSocket/SSE 等长连接推送，满足“准实时 + 实现简单”的折中。
 - 仍然允许通过系统级机制（如 systemd、Docker）启动和停止后端服务进程，本次重构不涉及这些外部运维机制的设计，仅确保后端以服务模式稳定运行即可。

### Key Entities *(include if feature involves data)*

- **后端服务实例（Backend Service）**：代表整个订阅系统的常驻进程，负责维持配置加载、任务调度、与外部服务（Alist、RSS 网站、WebDAV 等）的连接。关键属性包括：当前运行状态、启动时间、版本信息、资源占用等。
- **订阅监控任务（Subscription Monitor Job）**：表示对一组 RSS 源按配置的周期性轮询任务，关联配置中的订阅 URL、过滤规则和间隔时间等参数。关键属性包括：启用状态、最近一次检查时间、上次发现资源数量等。
- **下载任务（Download Task）**：代表从 RSS 提取出的单个或一组下载项，包括番剧名称、集数、下载链接（种子或磁力）、对应的网盘路径、当前下载和重命名状态等。与后端的下载管理器以及通知模块存在关联。
- **配置（Application Configuration）**：以结构化形式持久化保存的系统配置，涵盖通用参数、Alist 连接信息、订阅与过滤规则、重命名和 WebDAV 行为等。关键属性包括：版本/更新时间、各模块子配置以及与默认配置的差异。
- **维护任务（Maintenance Job）**：泛指由用户显式触发的运维类任务，如 WebDAV 嵌套目录修复。关键属性包括：任务类型、目标目录或资源、执行模式（预览/执行）、开始和结束时间、结果统计与错误列表等。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在一台全新环境中，从仅启动后端服务进程到完成基础配置并成功启动订阅监控，全流程仅通过浏览器操作可完成，且熟悉系统的用户可在 10 分钟内完成。
- **SC-002**: 在常规家庭/NAS 硬件环境下，仪表盘状态查询和最近日志加载接口在正常负载（订阅数和日志量中等）的前提下，95% 请求的响应时间不超过 2 秒。
- **SC-003**: 通过问卷或反馈统计，至少 80% 的典型用户在升级到新版本后，表示“日常操作基本不再需要登录命令行”，且可以独立完成启停与配置调整。
- **SC-004**: 在运行 30 天的观测期内，与“配置错误”“忘记重启服务”等相关的问题反馈/工单数量相较于仅命令行版本减少至少 30%。
